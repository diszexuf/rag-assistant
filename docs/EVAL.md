# Оценка качества

Результаты прогонов `eval.run_search` и `eval.run_generation`. Запросы — `backend/eval/queries.yaml` (24 запроса: 18 с ожидаемой операцией, 6 без) и `backend/eval/requests.yaml` (5 запросов генерации). Наборы написаны автором прототипа на четырёх учебных программах, поэтому цифры оптимистичны: см. [NOTES](NOTES.md).

Запуск:

```bash
docker compose exec backend python -m eval.run_search            # только вектор
docker compose exec backend python -m eval.run_search --rerank   # вектор + реранкер
docker compose exec backend python -m eval.run_generation --repeats 3
```

Результаты пишутся в `backend/eval/results/` (в репозиторий не попадают).

## Поиск

Метрики считаются по первым 5 кандидатам после фильтра (тип станка, тип операции, диалект) без отсечения порогом. `decision_accuracy` — доля запросов, где решение «найдено / не найдено» верно при пороге по первому кандидату.

|---|---|---|---|---|---|---|
| 14.10.2026 | хеши слов (`mock`) | 1.00 | 1.00 | 1.00 | 0.447 | верные кандидаты до 0.54, отрицательные от 0.36: порог не разделяет |
| 14.10.2026 | `bge-m3` | 1.00 | 1.00 | 1.00 | 0.314 | верные до 0.33, отрицательные от 0.30 |
| 14.10.2026 | `bge-m3` + `bge-reranker-v2-m3` | 1.00 | 1.00 | 1.00 | 0.78 (по 1 − оценка) | верные от оценки 0.16, отрицательные до 0.28 |

### Выбор порога

Ошибки двух видов: **пропуск верной** (операция есть, а система сказала «нет») — модель пишет операцию по подсказке диалекта; **ложное принятие** (операции нет, а образец подставлен) — модель получает чужой образец. Второе хуже, поэтому порог выбирается консервативно.

| Схема | Порог | Верных пропущено (из 18) | Ложно принято (из 6) | decision_accuracy |
|---|---|---|---|---|
| хеши слов | расстояние 0.5 (по умолчанию) | 2 | 2 | 0.83 |
| bge-m3 | расстояние 0.3 | 2 | 1 | 0.88 |
| bge-m3 | расстояние 0.35 | 0 | 3 | 0.88 |
| bge-m3 | расстояние 0.5 | 0 | 5 | 0.79 |
| bge-m3 + реранкер | оценка ≥ 0.3 | 2 | **0** | **0.92** |
| bge-m3 + реранкер | оценка ≥ 0.2 | 1 | 2 | 0.88 |
| bge-m3 + реранкер | оценка ≥ 0.15 | 0 | 3 | 0.88 |

Выводы:

- **Ранжирование внутри фильтра верное во всех схемах** (hit@1 = 1.00): в базе по 1–2 операции каждого типа на диалект, поэтому ранжировать почти нечего. Различия видны только в решении «найдено / не найдено».
- **bge-m3 лучше хешей слов:** перефразировки («проточить вал по ступеням», «просверлить сквозное отверстие») получают расстояние до 0.33 против 0.54. Но у него высокий «фон»: непохожие операции того же типа лежат на 0.30–0.42, поэтому порог по одному расстоянию неоднозначен.
- **Реранкер разделяет лучше:** ни одного ложного принятия при оценке ≥ 0.3. Цена — два пропуска на сильных перефразировках («Нарезать метрическую резьбу М30 с шагом 1.5…», «Просверлить сквозное отверстие Ø20… сверло в позиции 11…»).
- **Значения по умолчанию:** `EMBEDDING_PROVIDER=tei` с `SEARCH_MAX_DISTANCE=0.35`, либо с реранкером `RERANKER_PROVIDER=tei` и `RERANK_MIN_SCORE=0.3`. Рекомендую вариант с реранкером. Проверить на реальных данных (см. NOTES): набор запросов написан тем же человеком, что и описания.

## Ресурсы (CPU, Docker Desktop, 15,6 ГБ)

| Контейнер | Память в покое | Прогрев | Замечание |
|---|---|---|---|
| `embeddings` (bge-m3, ONNX) | ~3,1 ГБ при `--max-batch-tokens 2048` | ~1 мин | при значении по умолчанию (16384) занимает ~10,8 ГБ |
| `reranker` (bge-reranker-v2-m3) | ~2,5 ГБ при `--max-batch-tokens 4096` | ~1 мин | |

При первом запуске обе модели скачиваются (по ~2,3 ГБ). Одновременный запуск двух контейнеров с настройками по умолчанию на этой машине привёл к убийству контейнера `embeddings` по памяти (код 137): поэтому в `docker-compose.yml` задан `--max-batch-tokens`.

Скорость на CPU: запрос на эмбеддинг одного короткого текста — около 100–130 мс (по логам TEI); оценка поиска по 24 запросам с реранкером — несколько секунд.

## Генерация

Базовая линия с живой моделью пока не снята: нужен `LLM_PROVIDER=gigachat`. Заполнить после прогона `eval.run_generation --repeats 3`.

Для справки: на заглушке (`DemoChatModel`, которая собирает программу из образцов без подстановки чисел) проверка чисел находит в среднем **1–9 пропущенных значений на запрос** (запросы 1–5 → 3, 6, 2, 1, 9). Это нижняя граница работоспособности проверки: заглушка копирует образцы, а проверка видит, что чисел запроса в программе нет.
