# Итоги прототипа: заметки для плана разработки

Прототип делался, чтобы обкатать пайплайн генерации УП и понять, что закладывать в план разработки MVP. Основная часть описана по состоянию на 12.10.2026 (работа остановлена на наброске); что изменилось после доработки 14.10.2026 — в последнем разделе. Как пользоваться и как устроено — в [GUIDE](GUIDE.md), исходный план — в [PLAN](PLAN.md).

## Что подтвердилось

- **Пайплайн собирается и работает целиком:** запрос списком операций → поиск источника по каждой операции → сборка УП одним вызовом модели → валидатор → исправление по отчёту → ответ с источниками.
- **Запрос как список операций — удачное решение.** Тип операции из справочника даёт надёжный фильтр, а поиск идёт по каждой операции отдельно.
- **Порог расстояния отделяет «найдено» от «не найдено».** На тестовых запросах подходящие операции оказывались на расстоянии 0,1–0,3, неподходящие — около 0,75 при пороге 0,5.
- **Ослабление фильтра работает:** при отсутствии программ для нужного материала берётся операция для другого материала на том же диалекте.
- **Фоновый запуск с SSE решает проблему долгого запроса.** Генерация занимает 15–40 секунд; стадии и таймер видны в интерфейсе.
- **Цикл доработки полезен.** На ошибках оформления он сокращал число замечаний (в одном прогоне с 23 до 2) и останавливался, когда попытка не давала улучшения.
- **Контракты между модулями выдержали.** Адаптер модели, валидатор и конвертер подключены через три функции и меняются независимо.

## Главный вывод

Узкое место — не поиск и не архитектура, а модель. Базовая `GigaChat` плохо справляется с задачей «взять образец и заменить в нём числа»:

- на один и тот же запрос даёт разные программы;
- размеры из запроса подставляет не всегда, часть значений остаётся из образца;
- пример из подсказки переносит дословно, вместе с его числами;
- может пропустить вызов инструмента или режимы для операции;
- вопреки инструкции пишет комментарии в чужом синтаксисе — их пришлось вырезать программно.

Подбор промптов улучшил результат, но не сделал его надёжным. Дальнейшая работа с промптами на этой модели даёт мало.

## Что не подтверждено

- **Качество поиска на реальных данных.** В базе четыре программы и десять операций, описанных в одном стиле; тестовые запросы писал тот же человек. На таких данных поиск выглядит лучше, чем будет в жизни.
- **Корректность G-кода.** Примеры в базе взяты из лабораторных программ с упрощениями, подсказки по циклам (`G76`, `G83`, `CYCLE83`, `CYCLE97`) составлены без проверки специалистом.
- **Запрос на резьбу в проверке совпал с примером из подсказки,** поэтому результат по операциям без источника завышен.
- **Сценарии таймаута и обновления страницы во время генерации** реализованы, но не запускались.

## Что упрощено относительно ТЗ

| В ТЗ | В прототипе |
|---|---|
| Токарная и фрезерная обработка | Только токарная |
| Конвертер диалектов | Заглушка: операция с другого диалекта считается ненайденной |
| Смысловые эмбеддинги | Векторы на хешах слов, поиск по совпадению слов |
| Документация станков в базе знаний | Короткие подсказки по типам операций в описании диалекта |
| Каталог инструмента | Список позиций в карточке станка |
| Редактор с подсветкой строк | Текстовое поле и список замечаний |
| 6 станков, 12 программ | 2 станка, 4 программы |

Валидатор сделан в объёме пяти проверок: синтаксис, известность команд, конец программы, инструмент из магазина, предел оборотов. Он проверяет форму программы, а не смысл.

## Что закладывать в план разработки

По убыванию влияния на результат.

1. **Надёжность подстановки чисел.** Варианты, которые стоит сравнить:
   - более сильная модель (`GigaChat-2-Pro`, `GigaChat-2-Max`) на тех же запросах;
   - разделение задачи: модель извлекает параметры операции в структурированном виде, а код подставляет их в шаблон операции. Это снимает с модели работу, с которой она справляется хуже всего;
   - проверка в валидаторе, что числа из запроса присутствуют в программе.
2. **Смысловые эмбеддинги.** У GigaChat это отдельный платный пакет (запрос сейчас возвращает 402). Код готов: переключается переменной `EMBEDDING_PROVIDER` с перезагрузкой базы. Для закрытого контура понадобится локальная модель.
3. **Данные.** Реальные УП с разметкой операций и описаниями, которые пишет не автор тестовых запросов. Без этого нельзя оценить ни поиск, ни порог.
4. **Проверка специалистом** описаний диалектов, подсказок по циклам и примеров в базе.
5. **Оценка качества.** Набор запросов с ожидаемым результатом и повторные прогоны: из-за нестабильности модели один прогон ничего не доказывает.
6. **Конвертер диалектов.** Отдельная функция. Образец — конвертер AnyCNC: он покрывает токарные циклы, включая перестройку `G71` ↔ `CYCLE95`.
7. **Дополнительный функционал из раздела 10 ТЗ:** проверка УП администратором и пополнение базы знаний, авторизация, экраны базы знаний.

## Технические замечания

- Автоперезагрузка бэкенда в контейнере обрывает идущую генерацию при правке файлов; для демонстрации её лучше отключить.
- Корневые сертификаты Минцифры нужны внутри контейнера, хранилище Windows ему недоступно; файл лежит в `backend/certs/`.
- Ключ GigaChat хранится в `.env`, в репозиторий не попадает.
- Модель возвращает программу в произвольном оформлении: несколько блоков кода, комментарии, нумерация кадров. Разбор ответа должен быть терпимым к этому.

## Доработка по плану IMPROVEMENT_PLAN

Выполнено по [IMPROVEMENT_PLAN](IMPROVEMENT_PLAN.md) (этапы 0–6). Что сделано и что осталось проверить.

### Что сделано

| Этап | Результат |
|---|---|
| 0. Eval | `backend/eval`: 24 запроса для оценки поиска, 5 для генерации, скрипты `run_search` и `run_generation`; базовая линия в [EVAL](EVAL.md) |
| 1. Проверка чисел | `orchestrator/params.py`: числа из описаний операций и инструкции ищутся в программе, отсутствующие дают предупреждение `REQUEST_VALUE_MISSING` (на доработку не влияет) |
| 2. Промпты | system-роль, промпты без конкретных числовых примеров, самопроверка в ответе, режимы резания по материалам (`CUTTING_MODES`) |
| 3. Правка | запрос на изменение текущей программы: берётся актуальный текст (с ручными правками), результат — версия той же программы, diff версий в интерфейсе |
| 4. bge-m3 | адаптер TEI и контейнер `embeddings`; порог подбирается `eval.run_search` |
| 5. Ингестия | `kb/split.py` и `seed/ingest.py`: УП из файла → черновик YAML для проверки человеком |
| 6. Реранкер | `bge-reranker-v2-m3` в контейнере `reranker`, порог по оценке |

### Что не проверено

- **Живая модель.** Все прогоны и тесты шли на заглушках. Влияние новых промптов и режимов резания на подстановку чисел нужно снять через `eval.run_generation` на GigaChat (и, если доступна, на `GigaChat-2-Pro`) и записать в EVAL.
- **Режимы резания.** Значения в `CUTTING_MODES` взяты из общих справочников и не проверены технологом.
- **Эвристика ингестии** проверена на четырёх учебных программах; на реальных УП она может ошибаться (чужие циклы, макросы, подпрограммы). Поэтому результат — черновик для проверки.
- **Реранкер** на данных текущего размера (1–2 операции одного типа на диалект) практически ничего не переставляет; польза появится после загрузки реальных программ.

### Решения, которые стоит помнить

- Проверка чисел намеренно мягкая (предупреждение), чтобы не гонять доработку из-за ложных срабатываний. Если eval покажет, что модель по-прежнему подставляет чужие числа, следующий шаг — структурное извлечение параметров и подстановка кодом.
- Правка передаёт модели программу целиком. Чтобы изменения не проходили незаметно, интерфейс показывает diff с предыдущей версией.
- Гибридный поиск (BM25) не делался: реранкер видит код фрагмента и покрывает точные токены (`G76`, `T0101`). Вернуться, если eval покажет промахи на запросах с кодами команд.
