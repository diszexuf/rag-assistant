# Устройство важных блоков

Подробное описание того, как работают ключевые части бэкенда и клиента. Обзор попроще — в [GUIDE](GUIDE.md). Пути указаны относительно `backend/app`.

Порядок чтения соответствует пути запроса: описание диалекта → разбор G-кода → валидатор → модели → поиск → пайплайн → фоновые запуски → API → клиент.

## 1. Описание диалекта

Файлы `nc/dialects/*.yaml`, загрузка — `nc/dialect.py`.

Диалект описан данными, а не кодом. Один YAML-файл задаёт всё, что системе нужно знать о стойке:

| Поле | Назначение |
|---|---|
| `syntax` | Какой разбор применять: `fanuc` или `sinumerik` |
| `commands` | Допустимые команды с названиями. Используется валидатором и целиком уходит в промпт |
| `program_end` | Команды, которыми может заканчиваться программа |
| `spindle` | Команды постоянной скорости резания и способ задать предел оборотов: кадром (`G50 S…`) или присваиванием (`LIMS=…`) |
| `tool_format` | Как читать номер инструмента: `fanuc_tt` (в `T0101` позиция — первые цифры) или `plain` (`T1`) |
| `comment_syntax` | Формулировка для промпта исправления |
| `op_hints` | Подсказка модели: каким циклом выполняется каждый тип операции, с примером |

`load_dialect(code)` читает файл один раз и кеширует результат, поэтому после правки YAML нужен перезапуск бэкенда.

Чтобы добавить диалект, достаточно нового файла; имя файла становится кодом диалекта.

## 2. Разбор G-кода

`nc/parser.py`, структуры — `nc/types.py`.

`parse(text, dialect)` превращает текст в список кадров (`Block`). Пустые строки и строки `%` пропускаются, но номера строк сохраняются — по ним потом показываются замечания.

У кадра есть:

- `number` — номер из `N10`;
- `commands` — команды в нормализованном виде: `G01` → `G1`, `M03` → `M3`;
- `words` — остальные адреса со значениями: `X`, `Z`, `S`, `F`, `T`, `LIMS`;
- `unknown_names` — имена, которых нет в диалекте (у Sinumerik это может быть вызов подпрограммы);
- `comment` и `error` — текст комментария и описание синтаксической ошибки.

Разбор строки отличается по диалектам:

- **Fanuc.** Комментарии в круглых скобках вырезаются. Остаток читается как последовательность «буква + число». Всё, что в эту схему не укладывается, — синтаксическая ошибка кадра.
- **Sinumerik.** Комментарий — всё после `;`. Кроме пар «буква + число» распознаются вызовы со скобками (`CYCLE95("CONTUR",2,…)`), присваивания (`LIMS=1300`, `T="REZEC"`) и одиночные имена (`DIAMON`).

Парсер не вычисляет выражения, не разворачивает подпрограммы и не проверяет состав параметров цикла — аргументы цикла хранятся одной строкой.

## 3. Валидатор

`nc/validator.py`. Вход: текст, код диалекта, сведения о станке (`MachineInfo`: предел оборотов и занятые позиции магазина). Выход: `ValidationReport` со списком замечаний; у каждого — строка, код, уровень (`error` или `warning`) и текст.

Пять проверок:

| Код | Как работает |
|---|---|
| `SYNTAX` | У кадра заполнено поле `error` после разбора |
| `UNKNOWN_COMMAND` | Команда кадра отсутствует в `commands` диалекта |
| `NO_PROGRAM_END` | В последнем непустом кадре нет ни одной команды из `program_end` |
| `TOOL_NOT_IN_MAGAZINE` | Номер позиции из адреса `T` не входит в список позиций станка. Именованный инструмент (`T="…"`) и `T0` не проверяются |
| `SPINDLE_LIMIT` | Значение `S` либо предел оборотов превышает лимит станка |

Проверка оборотов — единственная, которая помнит состояние между кадрами. Валидатор отслеживает, включена ли постоянная скорость резания (`G96`/`G97`): при `G96` число после `S` означает метры в минуту, и сравнивать его с оборотами нельзя. Кадр ограничения (`G50 S…` или `LIMS=…`) сравнивается с лимитом всегда.

Неизвестное имя в Sinumerik даёт предупреждение `UNKNOWN_NAME`, а не ошибку: это может быть законный вызов подпрограммы.

Без сведений о станке выполняются только первые три проверки.

Чего валидатор не делает: не проверяет геометрию, параметры циклов, наличие подачи и включённого шпинделя перед резанием, соответствие программы запросу. Отсутствие замечаний означает только корректную форму.

## 4. Обращение к моделям

`llm/`.

### Интерфейсы

`llm/base.py` задаёт три протокола:

```python
class ChatModel(Protocol):
    async def complete(self, messages: list[ChatMessage], **params) -> str: ...

class EmbeddingModel(Protocol):
    async def embed(self, texts: list[str]) -> list[list[float]]: ...

class Reranker(Protocol):
    async def rerank(self, query: str, texts: list[str]) -> list[float]: ...
```

Остальной код знает только о них. `llm/factory.py` выбирает реализацию по `LLM_PROVIDER`, `EMBEDDING_PROVIDER` и `RERANKER_PROVIDER` из `.env` — чат, эмбеддинги и реранкер настраиваются независимо. Реализации: GigaChat (чат и эмбеддинги), Text Embeddings Inference (`llm/tei.py`: эмбеддинги bge-m3 и реранкер), заглушки (чат и эмбеддинги). Чтобы добавить другого поставщика, нужен класс с нужным методом и ветка в фабрике.

### Адаптер GigaChat

`llm/gigachat.py`, класс `GigaChatClient` реализует оба протокола.

- **Токен.** Ключ из `.env` обменивается на токен доступа, который живёт около получаса. Токен запрашивается при первом вызове и обновляется за минуту до истечения. Блокировка не даёт двум одновременным вызовам запросить его дважды.
- **Повторы.** Сетевой сбой, ответ 429 и ошибки 5xx повторяются до двух раз с паузой. Ошибки запроса (4xx) не повторяются: повтор не поможет. Ответ 401 сбрасывает токен.
- **Сертификаты.** К системным добавляются сертификаты Минцифры из файла `GIGACHAT_CA_BUNDLE`.
- **Журнал.** Каждый вызов пишет в лог модель, длительность и число токенов.

Любая неудача превращается в `LLMError` — единственное исключение, которое обязан обрабатывать вызывающий код.

### Заглушки

`llm/mock.py`:

- `ScriptedChatModel` — отдаёт заранее заданные ответы по очереди; используется в тестах, в том числе чтобы подсунуть программу с ошибкой или отказ модели;
- `DemoChatModel` — склеивает программу из фрагментов, найденных в промпте; позволяет показать работу системы без сети;
- `HashEmbeddingModel` — эмбеддинги без нейросети (см. следующий раздел).

## 5. Векторы и поиск

`kb/ingest.py`, `kb/search.py`, `llm/mock.py`.

### Какой текст превращается в вектор

И для операции в базе, и для операции в запросе вектор строится по одной и той же строке — `embedding_text()`:

```
<название типа операции>. <описание>
```

Сам G-код в вектор не попадает: ищем по описанию, а не по коду.

### Как строится вектор сейчас

`HashEmbeddingModel` делает вектор из 1024 чисел так:

1. текст приводится к нижнему регистру и режется на слова;
2. слова короче трёх букв отбрасываются, числа остаются;
3. от слова берутся первые пять букв — грубая замена приведению к основе, чтобы «точение» и «точения» совпали;
4. хеш этого обрубка даёт номер ячейки, ячейка увеличивается на единицу;
5. вектор нормируется к единичной длине.

Два текста получаются близкими, если у них много общих слов. Синонимы и перефразировки так не находятся.

### Эмбеддинги bge-m3

`EMBEDDING_PROVIDER=tei` включает модель `BAAI/bge-m3` (1024 измерения, как в схеме). Она работает в отдельном контейнере `embeddings` (Hugging Face Text Embeddings Inference, CPU, образ `cpu-1.9`), бэкенд обращается к нему по HTTP через `TEIEmbeddingModel` (`llm/tei.py`): пакеты по 32 текста, нормировка вектора на стороне сервера, проверка размерности. Контейнер модель не хранит в образе: она скачивается при первом запуске в том `hf_cache` (~2,3 ГБ) и дальше берётся из него. Процессору нужно ~3 ГБ памяти: для этого в `docker-compose.yml` задан `--max-batch-tokens 2048` (со значением по умолчанию ONNX Runtime занимает ~11 ГБ, а запуск вместе с реранкером убивает контейнер по памяти, см. [EVAL](EVAL.md)).

После смены провайдера эмбеддингов базу знаний нужно загрузить заново (`python -m seed.seed --reset`) и пересчитать порог (`python -m eval.run_search`): расстояния у bge-m3 другие, чем у хешей слов.

Если CPU-образ TEI не запустит bge-m3, запасной вариант — сервис Infinity (`michaelf34/infinity`, один контейнер на эмбеддинги и реранкер, API в формате OpenAI). Менять придётся только разбор ответа в адаптере.

### Запрос к базе

`search_operations()` в `kb/search.py`:

1. **Фильтр по метаданным:** статус программы `confirmed`, тип станка, тип операции; по условию — диалект (тот же либо любой другой) и материал.
2. **Сортировка по косинусному расстоянию** между вектором запроса и векторами операций — это делает расширение pgvector.
3. **Без реранкера:** результаты с расстоянием больше `SEARCH_MAX_DISTANCE` отбрасываются уже в коде, остаётся `SEARCH_TOP_K` лучших.
4. **С реранкером** (`RERANKER_PROVIDER=tei`): из базы берутся `SEARCH_CANDIDATES` (20) ближайших без отсечения по расстоянию; для каждого строится текст «тип. описание + код фрагмента» и реранкер (cross-encoder `BAAI/bge-reranker-v2-m3` в контейнере `reranker`) оценивает его вместе с запросом. Остаются кандидаты с оценкой не ниже `RERANK_MIN_SCORE`, лучшие первыми, не больше `SEARCH_TOP_K`. Оценка (0..1) показывается в интерфейсе как «релевантность».

Расстояние 0 — векторы совпадают, 1 — общих слов нет. Чем больше оценка реранкера, тем операция релевантнее.

Реранкер читает запрос и кандидата вместе, поэтому точнее векторного сравнения и видит код фрагмента (циклы, режимы). Пользу он даёт, когда операций одного типа в базе много.

### Оценка поиска

`python -m eval.run_search` прогоняет запросы из `backend/eval/queries.yaml` и считает hit@1, hit@3, MRR, точность решения «найдено / не найдено» и рекомендуемый порог. Флаг `--rerank` оценивает схему с реранкером (расстоянием считается 1 − оценка). Результаты сравнения — в [EVAL.md](EVAL.md).

### Ингестия УП из файла

`app/kb/split.py` и `seed/ingest.py`. Нарезка работает на разборе `nc.parse`:

1. концовка — хвост программы из кадров только с командами конца и остановов (`M5`, `M9`, `M30`…);
2. операция начинается с вызова инструмента (`T…`), повторный вызов до первого рабочего перемещения операцию не делит;
3. тип по командам: резьба (`G76`, `G92`, `CYCLE97`) → сверление (`G83`, `G81`, `CYCLE82`, `CYCLE83`…) → точение (`G71`, `G70`, `G90`, `CYCLE95`) → подрезка (`G94`); без циклов — по линейным перемещениям: `G1` по X в ноль или отрицательное значение без Z — подрезка, `G1` по Z на длину больше 1 мм — точение;
4. признаки операции (инструмент, циклы, диапазоны X и Z, скорость или частота, подача) идут в описание: модель получает код и пишет описание (`prompts/describe.md`), без модели — шаблон по признакам.

Результат — YAML-черновик в формате `seed/programs/*.yaml`; в базу он попадает только после проверки человеком и `python -m seed.seed`. Тест `test_split.py` проверяет, что нарезка собранных seed-программ совпадает с их ручной разметкой.

### Загрузка базы знаний

`seed/seed.py` читает YAML-файлы программ. Программа в файле разбита на шапку, операции и концовку; `assemble()` склеивает их в один текст и запоминает, какие строки занимает каждая операция. Поэтому номера строк не нужно считать руками. Фрагмент операции потом берётся из текста программы по этим номерам (`Operation.fragment()`).

## 6. Пайплайн генерации

`orchestrator/pipeline.py`, класс `Pipeline`, метод `run()`.

Пайплайн не знает о базе и HTTP: поиск, конвертер, валидатор и модель передаются ему снаружи. Благодаря этому он целиком проверяется тестами с подставными функциями.

### Шаг 1. Источник для каждой операции

`_resolve_source()` делает до четырёх поисков, от строгого к мягкому:

| Попытка | Диалект | Материал | Результат при находке |
|---|---|---|---|
| 1 | тот же | тот же | источник `kb` |
| 2 | тот же | любой | источник `kb` |
| 3 | другой | тот же | конвертер |
| 4 | другой | любой | конвертер |

Берётся ближайшая находка. Если найденная операция на другом диалекте, её фрагмент отдаётся конвертеру. Конвертер возвращает текст и список непереведённых кадров; если список не пуст, операция получает источник `unknown` с пояснением. Сейчас конвертер — заглушка, которая возвращает непереведённым всё.

Если ни одна попытка ничего не дала — `unknown` с пояснением «В базе знаний нет похожих операций».

### Шаг 2. Промпт

Модели уходят два сообщения:

- **system** (`prompts/system.md`) — роль и общие правила: только команды диалекта, только инструмент станка, без комментариев, числа из описания обязательно переносить в программу, формат ответа;
- **user** — шаблон `prompts/generate.md`, заполненный значениями:
  - станок, диалект, материал, предел оборотов, особенности станка;
  - инструмент по позициям магазина;
  - блок на каждую операцию: тип, описание, подсказка диалекта для этого типа (`op_hints`, числа в ней заменены заполнителями вроде `<глубина>`) и фрагмент-образец в блоке кода;
  - рекомендуемые режимы резания для материала (`CUTTING_MODES`) — только для типов операций запроса;
  - правила работы с образцом (без конкретных чисел в примерах: иначе модель переносит их дословно);
  - полный список допустимых команд диалекта.

Модель вызывается один раз на всю программу, а не на каждую операцию: ей нужно самой составить начало, переходы между операциями и концовку. В ответе она перечисляет, куда подставила числа из описаний.

### Шаг 3. Разбор ответа

- `extract_program()` ищет в ответе блоки кода. Если их несколько, берётся самый длинный: модель иногда выдаёт черновик и итог отдельными блоками. Текст вне блоков становится пояснением в чате.
- `strip_comments()` вырезает комментарии, написанные в чужом синтаксисе (`%`, `//`, `--`, для Fanuc ещё `;`), и пустые строки.

Если блока кода в ответе нет, запуск завершается ошибкой «Модель не вернула текст программы».

### Шаг 4. Проверка и исправление

Программа проходит валидатор. Пока есть ошибки и не исчерпан лимит `MAX_FIX_ATTEMPTS`:

1. модели отправляется шаблон `prompts/fix.md` с текущей программой и списком ошибок по строкам;
2. исправленный вариант снова проходит валидатор;
3. если ошибок стало меньше — вариант принимается; если столько же или больше — цикл останавливается и остаётся предыдущий вариант.

Предупреждения цикл не запускают. Программа с оставшимися ошибками всё равно отдаётся пользователю вместе с отчётом.

К отчёту валидатора добавляется проверка чисел (`orchestrator/params.py`, метод `Pipeline._check`): из описаний операций регулярными выражениями извлекаются диаметры, длины, глубины, скорость, обороты, подача, шаг резьбы и номер инструмента, и каждое значение ищется среди чисел программы (адреса X, Z, S, F, T и аргументы циклов Sinumerik). Нет значения — предупреждение `REQUEST_VALUE_MISSING` без номера строки (строка 0). Проверка идёт по всей программе: границ операций в сгенерированном тексте нет. Регрессия на ложные срабатывания: тест прогоняет её по всем образцам базы знаний.

### Правка готовой программы

`Pipeline.edit()`. Запрос с `base_program_id` не создаёт новую программу, а изменяет существующую:

1. берётся текущий текст программы (`programs.text`, он уже включает ручные правки);
2. если в запросе есть новые операции, для них выполняется поиск источников (шаг 1), нумерация продолжается после уже имеющихся;
3. шаблон `prompts/edit.md`: текущая программа, инструкция технолога, новые операции с образцами, режимы резания, допустимые команды; требование менять только то, о чём просят;
4. дальше то же, что в шагах 3–5: разбор ответа, валидатор, цикл исправления;
5. числа проверяются по новым операциям и по тексту инструкции (старые описания не проверяются: инструкция может менять их значения);
6. результат сохраняется новой версией той же программы (`author = edit`), источники новых операций добавляются в `programs.sources`, метка пересчитывается по всем источникам.

### Шаг 5. Итог

`worst_origin()` определяет метку программы как худший из источников её операций: `unknown` хуже `converted`, `converted` хуже `kb`.

По ходу работы пайплайн записывает промежуточное состояние в объект `RunProgress`. Если запуск оборвётся на исправлении, уже полученный черновик не пропадёт.

## 7. Фоновые запуски

`orchestrator/runs.py`, класс `RunManager`. Существует в одном экземпляре, создаётся при старте приложения в `main.py`.

Зачем: генерация длится десятки секунд, и HTTP-запрос не должен висеть всё это время.

Как устроено:

1. `start()` создаёт запись запуска в таблице `generation_runs` со стадией `queued` и запускает фоновую задачу `asyncio`. HTTP-запрос сразу возвращает номер запуска.
2. Фоновая задача (`_execute`) выполняет пайплайн. Перед каждым шагом пайплайн вызывает функцию, которая записывает новую стадию в базу и рассылает её подписчикам.
3. По окончании `_save_result()` создаёт программу, её первую версию с отчётом валидатора и сообщение-ответ в чате. Для правки (`progress.base_program_id`) вместо новой программы добавляется версия к существующей (`_save_edit()`).

Стадии: `queued` → `searching` → `converting` → `generating` (при правке — `editing`) → `validating` → `fixing` → `done` либо `failed`.

**Подписка.** `stream()` — источник событий для SSE. Сначала он отдаёт текущее состояние запуска из базы, затем — изменения из очереди. Поэтому клиент, подключившийся в середине или после обрыва связи, сразу узнаёт актуальную стадию. Раз в 15 секунд без событий отправляется пустой «пульс», чтобы соединение не закрылось.

**Сбои.** Общий таймаут `RUN_TIMEOUT_S`, отказ модели и любое другое исключение переводят запуск в `failed` с текстом причины; запуск не может остаться в активной стадии. Если к моменту сбоя черновик программы уже был, он сохраняется с пометкой «Черновик».

**Перезапуск сервера.** Фоновые задачи живут в памяти процесса. При старте `fail_stale_runs()` помечает все незавершённые запуски как `failed` — выполнять их уже некому.

Ограничение: очереди подписчиков тоже в памяти, поэтому схема рассчитана на один процесс сервера.

## 8. HTTP-интерфейс

`chat/api.py`. Все адреса начинаются с `/api`.

| Метод и адрес | Назначение |
|---|---|
| `GET /refs` | Справочники: станки с инструментом, материалы, типы операций |
| `GET /chats`, `POST /chats` | Список чатов; создание чата со станком и материалом |
| `GET /chats/{id}` | Чат с сообщениями и состоянием активного и последнего запуска |
| `DELETE /chats/{id}` | Удаление чата с его программами |
| `POST /chats/{id}/requests` | Новая программа: `operations`. Правка: `base_program_id` и `instruction` и/или новые `operations`. Ответ 202 с номером запуска |
| `GET /runs/{id}` | Состояние запуска |
| `GET /runs/{id}/events` | Поток событий запуска (SSE) |
| `GET /programs/{id}` | Программа: источники и все версии с отчётами |
| `POST /programs/{id}/versions` | Ручная правка: проверка валидатором (и проверка чисел по описаниям операций) и сохранение новой версии |

Особенности:

- входа нет: `current_user()` возвращает единственного предустановленного пользователя;
- второй запрос в чате, пока идёт генерация, отклоняется с кодом 409;
- ручная правка сохраняется всегда; замечания валидатора записываются в версию, но сохранению не мешают.

Интерактивное описание всех адресов — http://localhost:8000/docs.

## 9. Хранение

`kb/models.py`, `chat/models.py`. Схема создаётся миграциями Alembic из `backend/alembic/versions`.

Три момента, которые не очевидны из названий таблиц:

- **Программы базы знаний и сгенерированные программы лежат в одной таблице `programs`.** Их различают поля `status` (`confirmed` у загруженных, `generated` у созданных в чате) и `origin`. В поиск попадают только `confirmed`.
- **Текст программы хранится дважды:** актуальный — в `programs.text`, вся история — в `program_versions`. Каждая генерация, ручная правка и правка по запросу добавляет версию со своим отчётом валидатора; автор версии — `system`, `user` или `edit`.
- **Источники операций хранятся в самой программе** (`programs.sources`, JSON): что было найдено, на каком расстоянии и почему операция осталась без источника.

## 10. Клиент

`frontend/src`.

- `api.ts` — функции запросов к серверу и описания типов ответов.
- `store.ts` — всё состояние экрана: справочники, чаты, открытый чат, открытая программа, текущий запуск.
- `App.vue`, `components/RequestForm.vue`, `components/ProgramPanel.vue` — три колонки экрана на компонентах Naive UI.

Самое важное место — функция `watchRun()` в `store.ts`:

1. открывает `EventSource` на `/api/runs/{id}/events`;
2. каждое событие обновляет стадию на экране;
3. раз в секунду обновляется таймер; если за `VITE_RUN_TIMEOUT_S` секунд завершающее событие не пришло, соединение закрывается и показывается ошибка ожидания;
4. завершающее событие перечитывает чат и открывает созданную программу.

Клиентский таймаут (300 с) намеренно больше серверного (280 с): сервер должен успеть сам завершить запуск и сообщить причину.

При открытии чата `store.ts` проверяет, нет ли в нём активного запуска, и если есть — снова вызывает `watchRun()`. Так ожидание продолжается после обновления страницы.

## 11. Тесты

`backend/tests`.

- `test_nc.py` — парсер обоих диалектов и по тесту на каждую проверку валидатора.
- `test_pipeline.py` — пайплайн на подставных поиске, конвертере и модели: три вида источников, порядок ослабления фильтра, цикл исправления и его остановка, отказ модели, сохранение черновика, разбор ответа, system-сообщение и режимы резания в промпте, правка программы.
- `test_params.py` — проверка чисел запроса, в том числе регрессия на образцах базы знаний.
- `test_split.py`, `test_ingest.py` — нарезка УП на операции и черновики ингестии; сверка с ручной разметкой образцов.
- `test_tei.py`, `test_rerank.py` — адаптеры TEI на подставном HTTP и отбор по оценке реранкера.
- `test_eval.py` — метрики оценки поиска и согласованность набора запросов с образцами.

Тесты не используют базу данных и сеть. Не покрыты тестами: SQL-запрос поиска, фоновые запуски, HTTP-интерфейс и клиент — они проверялись вручную и прогоном сценариев через API.
