# План доработки: качество генерации и RAG

Документ — задание для исполнителя (человека или модели), который вносит изменения в код. Каждый этап самодостаточен: цель, файлы, точные изменения, тесты, критерий готовности. Этапы выполняются по порядку, каждый — отдельным коммитом.

Перед началом прочитайте [GUIDE](GUIDE.md), [INTERNALS](INTERNALS.md) и [NOTES](NOTES.md). Главный вывод NOTES: узкое место — не поиск, а модель, которая не подставляет числа из запроса. Поэтому сначала идут этапы, улучшающие генерацию (1–3), затем инфраструктура RAG (4–6).

## Общие правила

- **Стиль кода.** Как в окружающем коде: комментарии и докстринги на русском, их мало и они объясняют «почему»; `dataclass` для структур; модули `app/nc` и `app/llm` не импортируют БД и FastAPI. Не добавлять зависимости без необходимости.
- **Проверка.** После каждого этапа: `docker compose exec backend pytest` — все тесты зелёные. Для клиента: `cd frontend && npm run build` (включает `vue-tsc --noEmit`).
- **Заглушки.** Всё должно работать при `LLM_PROVIDER=mock` и `EMBEDDING_PROVIDER=mock` без сети. Новая функциональность модели поддерживается в `DemoChatModel` ([mock.py](../backend/app/llm/mock.py)) хотя бы минимально.
- **Не трогать:** конвертер (`app/nc/converter.py`), существующие пять проверок валидатора, механизм фоновых запусков и SSE.
- **Документация.** В конце каждого этапа обновить затронутые места в README, GUIDE, INTERNALS, TESTING и `.env.example`.
- **Git.** В репозитории ещё нет коммитов. Перед этапом 0 сделать начальный коммит текущего состояния. Сообщения коммитов на русском, по одному коммиту на этап.

## Этап 0. Eval-набор

**Цель:** измерять эффект следующих этапов. Без этого нельзя сказать, стало ли лучше, и нельзя подобрать порог.

### Файлы

```
backend/eval/
  __init__.py
  queries.yaml        # запросы для оценки поиска
  requests.yaml       # многооперационные запросы для оценки генерации
  run_search.py       # python -m eval.run_search
  run_generation.py   # python -m eval.run_generation
  results/            # результаты прогонов, в .gitignore
```

Добавить `backend/eval/results/` в `.gitignore`.

### queries.yaml

Список записей:

```yaml
- id: facing-fanuc-1
  machine: Токарный станок с ЧПУ Fanuc 0i-TD   # имя из seed/data/machines.yaml
  material: steel
  op_type: facing
  description: Подрезка торца заготовки диаметром 60 мм резцом T0101, 120 м/мин, подача 0.15
  expected: Втулка с центральным отверстием (Fanuc)   # title программы из seed/programs или null
```

`expected` — заголовок программы, операция которой должна найтись (в каждой программе не больше одной операции каждого типа, поэтому пара «программа + тип» однозначна). `null` — подходящей операции нет, правильный ответ «источника нет».

Состав (около 25 записей):
- для каждой из 10 операций в `seed/programs` — два запроса: близкий к описанию и перефразированный другими словами (синонимы: «торцевание» вместо «подрезки торца», «расточка», «проточка», «отверстие под …», другой порядок слов, без номера инструмента);
- 5 отрицательных: операция того же типа, но по смыслу другая (галтель фасонным резцом, внутренняя резьба метчиком, глухое отверстие под шпонку и т. п.);
- 5 запросов из примеров GUIDE (раздел 3) с ожидаемыми результатами оттуда.

Ожидаемый результат должен учитывать стратегию поиска: фильтр по типу станка, типу операции и диалекту станка запроса.

### run_search.py

Оценивает только поиск, без модели. Для каждой записи:

1. Загрузить станок по имени, собрать `SearchFilters(machine_kind, op_type, dialect=machine.dialect_code)` — **без материала** (ослабление по материалу проверяется тестами пайплайна).
2. Вызвать `search_operations(session, embedder, embedding_text(op_type, description), filters, top_k=5, max_distance=2.0)` — без отсечения порогом, чтобы видеть все расстояния. После этапа 6 — с реранкером, см. там.
3. Записать: ранг ожидаемой программы (или `None`), расстояние первого и ожидаемого кандидата.

Вывод в консоль и в `eval/results/search-<дата-время>-<embedding_provider>.json`:
- `hit@1`, `hit@3`, `MRR` по положительным запросам;
- точность решения «найдено / не найдено» при текущем `SEARCH_MAX_DISTANCE` по всем запросам (положительный считается верным, если первый кандидат — ожидаемый и проходит порог; отрицательный — если первый кандидат не проходит порог);
- таблица: id, ожидаемое, ранг, расстояние до ожидаемого, расстояние до лучшего — для подбора порога;
- рекомендуемый порог: середина между максимальным расстоянием верных первых кандидатов и минимальным расстоянием лучших кандидатов отрицательных запросов (если интервалы пересекаются — вывести предупреждение).

Использовать `SessionLocal` и `get_embedding_model()` из приложения. Аргумент `--max-distance` переопределяет порог.

### requests.yaml и run_generation.py

`requests.yaml` — 5 запросов из GUIDE (раздел 3, примеры 1–4 плюс один на три операции): станок, материал, список операций.

`run_generation.py --repeats N` (по умолчанию 3) прогоняет каждый запрос через `Pipeline` с текущим `get_chat_model()` (так же, как `RunManager._generate`, но без записи в БД) и считает по каждому прогону:
- число ошибок и предупреждений валидатора;
- после этапа 1 — число предупреждений `REQUEST_VALUE_MISSING` (пропущенные числа из запроса);
- время и число попыток доработки.

Итог: средние по запросу и общий итог, JSON в `eval/results/generation-<дата-время>-<модель>.json`. При `LLM_PROVIDER=mock` скрипт должен отрабатывать (как дымовой тест).

### Готово, когда

- `docker compose exec backend python -m eval.run_search` печатает метрики на хеш-эмбеддингах;
- результат прогона записан в новый файл `docs/EVAL.md`: дата, провайдер эмбеддингов, метрики, порог. Этот файл дополняется после этапов 1, 2, 4 и 6.

## Этап 1. Проверка чисел из запроса

**Цель:** технолог видит, какие размеры и режимы из описания операции не попали в программу. Это главная наблюдаемая ошибка модели.

### Новый модуль `backend/app/orchestrator/params.py`

```python
@dataclass(frozen=True)
class ExpectedValue:
    operation: int       # номер операции в запросе, с 1
    kind: str            # diameter | final_diameter | length | depth | cut_depth | allowance | speed | rpm | feed | tool | pitch
    value: float
    text: str            # фрагмент описания, из которого извлечено, — для сообщения

def extract_values(op_type: str, description: str, operation: int) -> list[ExpectedValue]: ...
def program_values(text: str, dialect: str) -> ProgramValues: ...
def missing_value_issues(text: str, dialect: str, operations: list[tuple[str, str]]) -> list[Issue]: ...
```

`operations` — пары `(op_type, description)`. Модуль импортирует только `app.nc`.

**Извлечение из описания** (регулярные выражения, регистр не важен, десятичная запятая приводится к точке, `Ø`/`ø`/`⌀` считаются словом «диаметр»):

| kind | Шаблон (суть) | Для каких операций |
|---|---|---|
| diameter | `диаметр\w*\s+(\d+(?:\.\d+)?)` или `Ø\s*(\d+…)` | facing |
| final_diameter | `до\s+(?:диаметра\s+)?(\d+…)\s*мм` | turning |
| length | `длин\w*\s+(\d+…)` | turning, threading |
| depth | `глубин\w*\s+(?:сверления\s+)?(\d+…)` (кроме «глубина резания») | drilling |
| cut_depth | `глубин\w*\s+резания\s+(\d+…)` | все |
| allowance | `припуск\w*\s+(\d+…)` | все |
| speed | `(\d+…)\s*м/мин` | все |
| rpm | `(\d+…)\s*об/мин` | все |
| feed | `подач\w*\s+(\d+…)` или `(\d+…)\s*мм/об` | все |
| tool | `\bT\s?(\d+)` | все |
| pitch | `М\d+(?:[.,]\d+)?\s*[хx×]\s*(\d+…)` | threading |

Диаметр в описании сверления — это диаметр сверла, его не проверять. Наружный диаметр резьбы и начальный диаметр точения не проверять (в программе их может не быть законно).

**Значения из программы** через `nc.parse`: все числовые значения слов (`Word.as_float()`), сгруппированные по адресу (`X`, `Z`, `U`, `S`, `F`, `T`, …), плюс все числа из аргументов вызовов циклов Sinumerik (слова с именем `CYCLE…()`; значение — строка аргументов через запятую, нечисловые и пустые пропускать). Сравнение по модулю с допуском `1e-6`.

**Правила проверки:**

| kind | Считается найденным, если |
|---|---|
| diameter (facing) | есть `X` со значением в диапазоне `[D, D + 5]` (подвод с запасом) |
| final_diameter | есть `X` = D или такое число среди аргументов цикла |
| length, depth | есть `Z` = L по модулю или такое число среди аргументов цикла |
| cut_depth, allowance | число встречается в любом адресе или аргументе цикла |
| speed, rpm | есть `S` = значение (в любом кадре) или такое число среди аргументов цикла |
| feed, pitch | есть `F` = значение или такое число среди аргументов цикла |
| tool | Fanuc (`tool_format: fanuc_tt`): есть `T`, у которого позиция (всё, кроме двух последних цифр) или полный номер совпадает с позицией из описания (T0101 ↔ T0101, T1 ↔ T0101); Sinumerik: `T` с тем же числом |

Проверка ведётся по всей программе, без привязки к строкам операции: модель может переставить кадры, а границ операций в сгенерированной программе мы не знаем.

**Замечание:** `Issue(line=0, code="REQUEST_VALUE_MISSING", severity="warning", message=f"Операция {n}: в программе нет значения «{text}»")`. Строка 0 — «относится к программе в целом».

### Встраивание

1. **Пайплайн** ([pipeline.py](../backend/app/orchestrator/pipeline.py)): ввести метод `_check(machine, program, operations) -> ValidationReport`, который вызывает `self._validate(...)` и добавляет к `report.issues` результат `missing_value_issues`, затем сортирует по строке. Использовать его везде вместо прямого `self._validate`. Цикл доработки по-прежнему считает только `report.errors`; предупреждения на него не влияют. Список операций хранить в `RunProgress` (поле `operations: list[tuple[str, str]]`), чтобы `_check` был доступен в цикле.
2. **Ручная правка** ([chat/api.py](../backend/app/chat/api.py), `save_version`): описания операций есть в `program.sources` (поля `op_type`, `description`). Добавить к отчёту `missing_value_issues(body.text, program.dialect_code, [(s["op_type"], s["description"]) for s in program.sources])`. У программ без `sources` проверка пустая.
3. **Клиент** ([ProgramPanel.vue](../frontend/src/components/ProgramPanel.vue)): если `issue.line === 0`, выводить сообщение без префикса «Строка N.».

### Тесты `backend/tests/test_params.py`

- извлечение по каждому `kind` на коротких описаниях, включая десятичную запятую и `Ø`;
- **регрессия на ложные срабатывания:** для каждой операции из всех `seed/programs/*.yaml` (использовать `seed.seed.assemble`) `missing_value_issues(фрагмент_операции, диалект, [(type, description)])` возвращает пустой список. Если какое-то правило даёт ложное срабатывание — уточнять правило, а не данные и не тест;
- программа с заменённой глубиной (`Z-42` вместо `Z-30` при «на глубину 30 мм») даёт ровно одно замечание с `kind` глубины;
- в `test_pipeline.py`: результат пайплайна содержит предупреждение, если `ScriptedChatModel` вернул программу без числа из описания, и `attempts == 0` (предупреждение не запускает доработку).

### Готово, когда

Тесты зелёные; в интерфейсе после генерации видны предупреждения о пропущенных числах; `eval.run_generation` выводит их число. Записать базовую линию в `docs/EVAL.md`.

## Этап 5. Ингестия УП из файла

**Цель:** загружать реальные программы без ручной разметки строк. Чтобы не делать новый путь записи в БД, ингестия выдаёт **черновик в формате `seed/programs/*.yaml`**: человек проверяет и правит его, переносит в `seed/programs/`, и обычный `seed.seed` загружает. Так проверка человеком встроена в процесс.

### Нарезка `backend/app/kb/split.py` (без БД)

```python
@dataclass
class OperationDraft:
    op_type: str | None      # None — тип определить не удалось
    line_start: int          # номера строк в исходном тексте, с 1
    line_end: int
    features: dict           # инструмент, команды, X/Z/S/F — для описания
    warnings: list[str]

@dataclass
class SplitResult:
    header: tuple[int, int] | None
    operations: list[OperationDraft]
    footer: tuple[int, int] | None

def split_program(text: str, dialect: str) -> SplitResult: ...
```

Алгоритм:
1. `nc.parse(text, dialect)`; блоки с `error` — в предупреждения.
2. **Границы операций:** кадр с адресом `T` (вызов инструмента) начинает новую операцию. Всё до первого такого кадра — шапка.
3. **Концовка:** с конца программы идут кадры, в которых только команды из `{M30, M2, M17, RET, M5, M9}` (и программный конец диалекта); они — концовка, а не часть последней операции.
4. **Тип операции** по командам внутри сегмента, в порядке приоритета:
   - threading: `G76`, `G92`, `G32` / `CYCLE97`, `G33`;
   - drilling: `G83`, `G81`, `G74` / `CYCLE81`, `CYCLE82`, `CYCLE83`;
   - turning: `G71`, `G70`, `G90` / `CYCLE95`, или кадры `G1` с перемещением по `Z` на длину больше 1 мм;
   - facing: `G94`, или кадр `G1` с `X ≤ 0` без `Z` в том же кадре;
   - иначе `None` и предупреждение.
   Если в сегменте признаки нескольких типов — взять первый по приоритету и добавить предупреждение «в операции признаки нескольких типов: …, проверьте разбиение».
5. `features`: номер инструмента, множество команд, диапазоны `X` и `Z`, значения `S` (с пометкой `G96`/`G97`), `F`, параметры циклов.

**Тест `tests/test_split.py` (критерий корректности):** для всех `seed/programs/*.yaml` склеить текст через `seed.seed.assemble`, прогнать `split_program` и сравнить с разметкой YAML: типы, `line_start`, `line_end` всех операций, границы шапки и концовки совпадают. Плюс отдельные случаи: программа без вызова инструмента, сегмент с признаками двух типов.

### Описание операции

- Промпт `backend/app/orchestrator/prompts/describe.md`: «Опиши операцию токарной обработки одним-двумя предложениями в стиле технолога: тип, размеры (диаметры, длины, глубины), инструмент, режимы, используемый цикл. Только то, что следует из кода; не придумывай». Подставляются диалект, тип, инструмент из карточки станка, фрагмент кода. Ответ — текст без блоков кода.

Описание по стилю должно быть похоже на описания в `seed/programs`: от этого зависит качество поиска.

### CLI `backend/seed/ingest.py`


## Этап 6. Rerank

**Цель:** выбирать лучший образец среди многих кандидатов и решать «найдено / не найдено» по оценке реранкера, а не по косинусному расстоянию. Пользу даёт, когда операций одного типа становится много (после этапа 5).

### Сервис

В `docker-compose.yml` — второй контейнер TEI с `--model-id BAAI/bge-reranker-v2-m3`, порт `8082:80`, тот же том `hf_cache`. Если на этапе 4 выбран Infinity, реранкер уже в том же контейнере. Проверка: `curl -s localhost:8082/rerank -H 'Content-Type: application/json' -d '{"query":"подрезка торца","texts":["Подрезка торца заготовки","Сверление отверстия"]}'`.

### Интерфейс и адаптер

- [base.py](../backend/app/llm/base.py): протокол `Reranker` с методом `async def rerank(self, query: str, texts: list[str]) -> list[float]` — оценки 0..1 в порядке `texts`.
- `tei.py`: `TEIReranker` — `POST {url}/rerank {"query", "texts", "truncate": true}`, ответ `[{"index", "score"}]` упорядочить по `index`.
- `config.py`: `reranker_provider: Literal["none", "tei"] = "none"`, `reranker_url = "http://reranker:80"`, `search_candidates: int = 20`, `rerank_min_score: float = 0.3` (подобрать на eval).
- `factory.py`: `get_reranker() -> Reranker | None`.

### Поиск ([search.py](../backend/app/kb/search.py))

- `OperationHit`: поле `score: float | None = None`.
- `search_operations(..., reranker: Reranker | None = None, candidates: int = 20, min_score: float = 0.3)`:
  - без реранкера — поведение как сейчас;
  - с реранкером: SQL берёт `candidates` ближайших **без** отсечения по расстоянию; тексты для реранкера — `f"{embedding_text(op_type, description)}\n{fragment}"` (код фрагмента помогает отличать циклы); `score` записывается в хиты; отсекаются хиты с `score < min_score`; сортировка по убыванию `score`; первые `top_k`.
- Отбор и сортировку после получения оценок вынести в чистую функцию `apply_rerank(hits, scores, min_score, top_k)` и покрыть тестом.
- [runs.py](../backend/app/orchestrator/runs.py): передавать реранкер и настройки в `search_operations`; `RunManager` получает фабрику `get_reranker` так же, как `get_embedding_model`.
- `OperationSource` ([pipeline.py](../backend/app/orchestrator/pipeline.py)): поле `score`, заполняется в `_with_hit`.

### Клиент

`Source` в `api.ts`: `score: number | null`. В `ProgramPanel` показывать «релевантность 0.87», если `score` есть, иначе расстояние, как сейчас.

### Оценка

`eval.run_search --rerank`: те же метрики, порог — по `score` (рекомендуемый `rerank_min_score` считать так же, как порог расстояния). Записать в `docs/EVAL.md` сравнение «bge-m3» и «bge-m3 + rerank».
